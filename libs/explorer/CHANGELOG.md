# Changelog

All notable changes to cfabric-browser will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Changed
- The menu no longer names the design the Parallel interface follows.
- The app is called CACCHT Explorer: next to its mark, in page and window titles, the macOS app (`CACCHT Explorer.app`), the downloads (`CACCHT-Explorer-*.zip`, `CACCHT-Explorer.mcpb`), the release titles, the MCP server's name, the citation and the messages. The package, command and module stay `cfabric-browser` / `cfabric_browser`; Context-Fabric stays the name of the core. The code moved from `libs/browser` to `libs/explorer`.
- Parallel's *Search* opens on *Template*, which now comes first, instead of *Search terms*; adding a search term from the word panel still switches to the terms.
- The browser works with either core, the Python one (`context-fabric` 0.5) and the Rust one (0.6.0rc1), and uses only their public API; CI tests it with both. Its displays (`cfabric_browser.display`), corpus registry (`cfabric_browser.registry`) and search cancel token (`cfabric_browser.cancel`) moved here from the core, where they were only on the browser's branches, with their tests and fixtures (`tests/fixtures`). Searches run through `S.search`: the worker checks the cancel token and the timeout between results, and ends a worker that doesn't stop in time. Templates are checked by the Python engine's cheap phases, or by `S.study` on the Rust core; the features per atom (export columns, statistics) come from a small parser of templates of the browser's own (`queries.template_atoms`), identical to the Python engine's on 81 templates.
- The standalone program is built on the Rust core (`context-fabric` 0.6.0rc1 from PyPI): searches are several times faster, and the first opening of a corpus prepares it in less time (the BHSA in 73 s instead of 186 s, here). It prepares a `.cfr` cache next to the corpus; a `.cfm` cache of the Python core is left alone.

### Fixed
- Hovering over a word of the SP showed a single letter (`sign`) unless the user had a local display file saying that words are its base type. The browser now has display settings of its own (`cfabric_browser/display_settings/`), layered under the local ones in `~/.cfabric/display`: for the SP, words as units, and for 7.2.4 the phrase labels and hidden atoms.
- `pyyaml` is a dependency of the browser's own: it was only there because the Python core brought it along, and the Rust core doesn't.

### Added
- The guide's chapters *Getting started*, *The datasets*, *The five ways of working*, *Reading and comparing*, *Words*, *Searching* (a short course in templates with counts from the BHSA guide), *The Concordance* and *Asking Claude* (the setup, moved from the release notes, which now link to it), with screenshots made by `frontend/scripts/screenshots.mjs` from the running program.
- A user guide (chapters still being written): Markdown in `guide/`, made into pages by `frontend/scripts/guide.mjs` during `npm run build`, served at `/guide/` (offline), with *Guide to …* in the interface menu; `--site DIR` writes the same pages for caccht.github.io. The packaging smoke test checks that the program serves it.
- Searching in plain language, the BHSA guide (`assistant/guides/bhsa.md`, given by `corpus_guide`): object types, the main features and their values in plain words, conventions (ETCBC transliteration, `[` and `/` endings, `=` for homonyms, Latin book names), templates in short, 42 worked examples with their counts, and common mistakes. A question set of 30 requests with correct templates and counts (`tests/data/bhsa-questions.yaml`); `tests/test_assistant_questions.py` checks both against the real BHSA with `CFABRIC_REAL_CORPORA=1`.
- Searching in plain language, connecting: the browser is an MCP server at `/mcp` (Streamable HTTP, stateless, JSON; only on 127.0.0.1, no web page as origin) with the tools `list_corpora`, `corpus_guide`, `describe_corpus`, `list_features`, `describe_feature`, `search_syntax_guide`, `check_template`, `try_search` and `propose_search`. `cfabric-browser mcp` is the same over stdio for apps that start their own servers (Claude Desktop): it passes each message on to the running browser and starts one if none runs; the standalone program takes `mcp` too. A Claude Desktop extension (`packaging/mcpb`, `Context-Fabric.mcpb` in the desktop release) does the same in Node.js. README: how to connect Claude Code, Claude Desktop and Antigravity CLI.
- Searching in plain language, proposals: a search proposed by a language model (`propose_search`, or `POST /api/proposals` with the browser's secret) appears as a card above the search form in Panes, Parallel and the Concordance, with the user's request, the template, the explanation and the trial's count, and *Run* / *Edit* / *Dismiss*; nothing runs by itself. The page follows proposals live (`/api/proposals/events`). Where a search came from (request, model, time, the proposed template) stays with it in the URL (`a0`, `ask`), in workspaces, when switching interfaces and in the citation, marked *(edited)* when the template was changed. The browser writes its address and a new secret to `~/.cfabric/running.json` at start, for a model's app to reach it. Monospace text no longer joins `=>` into an arrow.
- Searching in plain language, groundwork (`cfabric_browser/assistant/tools.py`): the tools a language model gets on the browser's open corpora: describing corpora and features and the template language (shared with `cfabric-mcp`), `check_template`, and `try_search`, a trial through the search pool (count up to 10,000 within 20 s, a few examples with their passages, and for an empty result the `feature=value` conditions whose value the feature never has). The browser now depends on `cfabric-mcp`.
- Linking the BHSA's lexemes to entries of BDB (`cfabric_browser/dictionaries/link.py`), the groundwork for BDB in the lexicon: the words of each verse are aligned with the Open Scriptures Hebrew Bible by their consonants, and a lexeme gets the BDB entries its words' lemmas lead to through Open Scriptures' lexical index.
- A lexeme's page for a frequent word (הלך, 1,547 occurrences) opened after about 20 s, because each word's book was looked up with `L.u`; the books are now found by slot range (0.5 s).
- BDB: a long entry (הלך, דבר) shows its stems folded under their first words.
- BDB elsewhere: the lexicon's *Find* searches BDB's short definitions, its rows show them, and it can be ordered *By root (BDB)*; the hover card and the inspector (*BDB entry*) give a word's entry, DSS words through the BHSA's lexeme; the Reader's *Lexicon* tab shows the definitions; the Interlinear has a line *BDB*. `bdb` in `/api/corpora/{c}/nodes/{n}/summary` and `/info`.
- BDB in the lexicon: a lexeme's page has a tab *BDB* with its entries (the text with verses that open the passage, references to other entries, abbreviations explained, neighbours, root family, Strong's and TWOT, a link to Sefaria). Added and removed in the library under *Dictionaries* or with `cfabric-browser add bdb [FILE]` / `remove bdb`; `/api/dictionaries`, `/api/dictionaries/{d}/entries/{id}`, and `bdb` in `/api/corpora/{c}/lexicon/{n}`. The file is published as release `v1.0` of `Context-Fabric/bdb` (CC BY-NC 4.0) and checked by its checksum; `add bdb FILE` adds one built here.
- Building the BDB dictionary file (`cfabric_browser/dictionaries/build.py`, run once for publishing): the text of every entry from Sefaria's *BDB Dictionary* and *BDB Aramaic Dictionary*, fetched one entry at a time with a pause between requests and kept in a checksummed cache (`sefaria.py`); joined to Open Scriptures' ids, parts of speech and short definitions by BDB's order and headwords; HTML reduced to a few tags, with references to verses as OSIS ids and to other entries as their ids (`bdb.py`); the lexemes linked, with corrections by hand in `corrections.yaml`; BDB's abbreviations. Joins by hand in `joins.yaml` for entries spelled otherwise and for neighbours with the same consonants that the join takes for each other; entries whose text stops short at Sefaria are marked `incomplete`, and the two entries Sefaria lacks get Open Scriptures' headword and short definition. Links checked against the verses BDB cites (`by_citations`): another entry of the same language and word class replaces the linked one when it cites the lexeme's verses clearly better; cross references and roots don't replace others.
- Downloading corpora (`cfabric_browser/downloads.py`): the BHSA (2021), the SP (7.2.4) and the DSS (2.0.1) from their own releases on GitHub, the files Text-Fabric uses, pinned by checksum. They are unpacked into `~/text-fabric-data/github` in Text-Fabric's layout with its `__checkout__.txt` files; names outside the corpus' folder are refused, and data folders already on the computer are left alone. *Open a corpus* lists those that are missing under *Can be downloaded*, with their size, licence (CC BY-NC 4.0 for all three) and terms of use; *Download* shows the progress and opens the corpus when it is there. Also `cfabric-browser download [NAME ...]` and the endpoints `/api/downloads`. The background jobs of translations and downloads share `cfabric_browser/jobs.py`.
- `--ask-downloads` (used by the standalone program): a first screen, *Getting the corpora*, offers the missing BHSA, SP and DSS with one *Download* button (nothing is downloaded without it; *Not now* is remembered), shows each corpus being downloaded, unpacked and prepared, and then goes on into the interface. *Cancel* stops the downloads; without a connection it offers *Try again*. A downloaded corpus is opened and loaded once right away, which compiles it (minutes for the BHSA and the DSS), so that later starts take seconds. `DELETE /api/downloads/{org}/{repo}` cancels a download; `askDownloads` in `/api/health`. `packaging/download-test.sh` downloads the SP in the standalone program with an empty home folder; CI runs it on all four builds.

### Changed
- Only two text formats: the BHSA's *Vocalized* (`text-orig-full`: vowels and accents, the qere where it differs) and *Unvocalized* (`text-orig-plain`: the ketiv's consonants); the other corpora only their full text, so *Display* offers a choice of text only for the BHSA. Transliterations, lexeme formats, the ketiv format and the DSS' word-level and source formats are no longer offered; a request for one of them (an old link, a saved workspace, `fmt=` in a download) gives the corpus' default text (`cfabric_browser/formats.py`). The comparison and the Concordance still choose their consonants from all of a corpus' formats.
- *Parallel* shows the reference corpus (the BHSA) as the first column when it chooses the texts itself, since the others are compared with the first.
- Translations as corpora, starting with the JPS 1917 (`cfabric_browser/translations/`): the builder downloads the 39 books from Sefaria's export, checks the title, the licence and the number of chapters and verses against the BHSA, removes the markup (a verse repeated in small type goes into `note`), and writes a corpus with words, verses, chapters and books (`text`, `trailer`, `lower`). Where the 1917 print divides verses differently (the Ten Commandments in Exodus 20 and Deuteronomy 5, and Numbers 25:19), the verses are divided as in the BHSA, and `printed` keeps the print's number.
- *Translations* in *Open a corpus*: *Add* downloads and builds a translation, shows the progress and opens it; *Remove* deletes it (at the next start when it is open). Also `cfabric-browser add [ID]` and `cfabric-browser remove ID`, and the endpoints `/api/translations`. The standalone program offers the JPS 1917.
- Translations in the interfaces: an English column in *Parallel*, *Panes* and the Reader, with the notes printed after verses and the print's verse numbers where it divides differently; a line per verse under the Interlinear (*Under*, heading *Translations*); English searches in the Concordance, sorted and collocated by `lower`; *Cite* names the edition. Translations are left out of the differences, and the hover card stays away for their words. Corpus cards and `/api/corpora` say whether a corpus is a translation (`translation`); `/passage` has `notes` and `printeds`, `/parallel` cells `note` and `printed`, and the Interlinear's `under` is a line (`translation`, `text`, `note`) for a translation.
- *Cite* in the Reader and the Interlinear (the chapter, or the verse chosen).
- *Concordance*, the fifth interface, after Sketch Engine and AntConc:
  - search results as lines with the hit in context, sorted by the hit or the words around it;
  - facets with counts that filter;
  - one line per verse, random samples, hits per 10,000 words, download of the lines;
  - collocations by logDice;
  - statistics.
  - New endpoints `/kwic`, `/kwic/facets` and `/collocations` under `/api/searches/{id}` (`cfabric_browser/concordance.py`). Values such as `NA` count as missing.
- *Interlinear*, the fourth interface, after STEPBible and BibleHub:
  - word blocks with lines of choice and order (transliteration, lexeme, gloss, part of speech, morphology, any feature);
  - another text word by word under them, with differences;
  - phrases and clauses with their function and type;
  - practice by hiding a line;
  - colours by part of speech or stem.
  - New endpoint `/api/corpora/{c}/interlinear` (`cfabric_browser/interlinear.py`), and `align_words` in `compare.py`, which pairs the words of two texts on their consonants.
- *Reader*, the third interface, after Sefaria:
  - one text in a quiet column, line by line or as running text in paragraphs (petuhah, setumah), chapter after chapter as one scrolls;
  - a panel about the clicked verse: *Parallels* (with differences), *Words*, *Lexicon*, *Search* (in *Parallel*) and *Notes* (the user's own notes and bookmarks, kept locally and in exported workspaces);
  - on a phone the panel opens from the bottom.
- An interface menu instead of the two-way switch, ready for five interfaces (*Panes*, *Parallel*, and the planned *Reader*, *Interlinear* and *Concordance*). Switching goes through one shared description of what is shown (`common.ts`), so that what one interface cannot show is kept for the next. Interfaces can be left out of the menu (*Choose which to offer…*, or `ui: hide:` in `browser.yaml`); `--ui` takes all five names, with `panes` for the classic interface. `/api/health` gives `hiddenUis`. Frontend tests with Vitest (`npm test`, also in CI)
- A second interface, *Parallel*, after Parabible's layout (`/Genesis/1?texts=bhsa,sp,dss`): a top bar with the chapter, its neighbours (also ←/→) and a drawer with the books, and a column per corpus that can be turned on and off, ordered and added from the library. Chapters follow the BHSA's numbering, a row per verse with a cell per corpus (`/api/parallel`); the DSS shows each scroll's text of the verse. Hovering over a word shows its card; clicking opens a word panel on the left (the inspector, with *Lexicon entry* for BHSA words). *Lexicon* in the top bar shows the lexicon; its verses open their chapter with the verse marked. *Differences* marks the words that differ from the first column, and with MT, SP and DSS, which scrolls agree with which per place. *Search* builds a search from words (*Add as search term* in the word panel: tick the features that count, choose verse, sentence, clause or phrase, and books) or takes a template; the results show each verse in every text (`/api/searches/{id}/parallel`), with statistics, download and citing as in *Panes*. Section items in `/sections` now carry their feature and its own value (`book`, `Jesaia`). *Display*, *Workspaces* (saved with their interface; loading one switches to it) and *Cite* (a citation per text) in its top bar; on a phone the texts of a verse are stacked. The standalone program starts in *Parallel*. A switch in both top bars goes between *Panes* and *Parallel* with the same passage and corpora; the last one used is remembered, `--ui` (or `ui:` in `~/.cfabric/browser.yaml`) sets the first. Corpus cards now have an `id` (`ETCBC/bhsa`) and `/api/health` the default `ui`.
- Hovering over a word shows a card with its essentials: gloss, lexeme, transliteration, part of speech and morphology (stem, tense, person, gender, number, state, suffix), in words rather than codes, read from the first feature of each role with a value, so also in the SP and the DSS, where the ETCBC's analysis (`_etcbc` features) comes first and the DSS's own fills the gaps; DSS words get their gloss from the BHSA's lexicon by their ETCBC lexeme (`lex_etcbc`) when the BHSA is open (`/api/corpora/{c}/nodes/{n}/summary`, `cfabric_browser/summary.py`). Clicking still opens the inspector, which now starts with the same essentials and folds the other features away; empty values and the `g_` features are left out unless asked for
- Lexicon, for a corpus with lexeme nodes and glosses (BHSA), after SHEBANQ's *Words* page: a third view besides *Read* and *Search*, with the lexemes per language and first letter (vocalised form, transliteration, gloss, part of speech, frequency), finding across all letters by Hebrew, transliteration or gloss, a filter by part of speech and sorting by frequency. A lexeme shows every verse it occurs in with its words marked, its distribution over the books (choose one to see only its verses), a search for it, and a TSV download of its occurrences (`/api/corpora/{c}/lexicon`, `/lexicon/{n}`, `/lexicon/{n}/occurrences`, `/lexicon/{n}/occurrences.tsv`); the lexeme is kept in the URL (`lx0=`)
- `--only ORG/REPO` (and `library: only:` in `~/.cfabric/browser.yaml`): limit the library to a few corpora, which are then also the only ones that can be opened from the browser. The standalone test version offers only BHSA, SP and DSS this way
- Program icon for the standalone program (Windows `.ico`, macOS `.icns`): the Context-Fabric mark in gold on a dark tile, drawn from `favicon.svg` by `packaging/make_icons.py`
- Standalone program: output and errors go to `~/.cfabric/logs/cfabric-browser.log`, with a message on Windows when it cannot start; without a window toolkit it opens a web browser instead. `--no-window` runs it as a plain server. Built and smoke-tested on Windows, macOS and Linux by the `browser-desktop.yml` workflow (`packaging/smoke-test.sh`)
- `--window`: the browser in a window of its own (pywebview) instead of a web browser; closing it stops the server. The window keeps its web storage (settings, saved workspaces) in `~/.cfabric/window`, and takes the first free port from 8107 so that it keeps the same address. The standalone program opens this window, without a console
- Start without corpora: `cfabric-browser` on its own opens an empty browser that offers the corpora on this computer (*Open a corpus*) straight away; the first corpus opened goes into the first pane. With `--no-library`, a corpus is still required
- Standalone program: `packaging/cfabric-browser.spec` builds `cfabric-browser` with PyInstaller into a program that needs no Python installation (`pip install .[desktop]`); `python -m cfabric_browser` also starts the browser
- `cfabric-browser` command: serve one or more corpora given by name (`bhsa`), repository or data directory
- JSON API: corpora, features, section tree, passages and nodes as render trees, node inspector, template check, search with live status events, paging, results in context, TSV export
- Searches in worker processes: parallel, cancellable, with time limits and a result cap; results stream in and are put in canonical order when done
- TSV export of all results: features mentioned in the template become columns per result node (`sp*` adds a feature without narrowing the search, as in Text-Fabric); `?excel=true` gives a UTF-16 file with byte-order mark that Excel opens correctly
- Several corpora side by side: up to four panes, each with its own corpus, view, passage and search, all kept in the URL
- Synchronised reading: opening a passage in one pane opens the corresponding passage in the others, through a concordance of book names (`1_Samuel`, `1Sam`, `Samuel_1`); where a verse is missing in a corpus, its chapter is shown with a note; reading panes without a passage (a short link such as `?c0=bhsa&ref0=Genesis+1&c1=sp&sync=1`, or a new pane) open the passage of the first pane that has one
- Search all corpora: run a template in every open corpus and compare the counts; each opens in its own pane
- Choose a corpus version with `@`: `DT-UCPH/sp@7.2.4`, or `@latest` for the newest on this computer (by default the version named in the corpus' app config); the corpus card reports the version actually loaded
- Reading by biblical book in a corpus of manuscripts (DSS), whose sections are scroll, fragment and line: an index of the words' `book`/`chapter`/`verse` gives per verse the text of every scroll that contains it (`/books`, `/witnesses?ref=Genesis 1`); synchronised reading aligns it with MT and SP (`align?view=books`). Reconstructed text is flagged (`dim`), also in the scroll view, and the DSS placeholders for lost text (`ε`) and illegible letters (`#`, `?`) are shown as in the editions, `[…]` and `◦`, while the transcription's morpheme breaks (`׳`, as in `עמ׳י`) are left out; in comparisons, an illegible letter counts as unknown; text the DSS also lists as non-biblical (`biblical=2`) is labelled. With Show differences, each scroll is compared with the MT or SP pane: reconstructed letters don't count, nor does what is lost at the edges of a fragment or next to a reconstruction; the MT/SP pane marks a word where any scroll differs, with a tooltip naming the scrolls (`compare?bview=books`)
- Three-way comparison: with MT, SP and a DSS pane in book view open and Show differences on, each place where MT and SP differ shows which scrolls side with MT, which with SP and which with neither, read only where a scroll preserves the text; as a line per place under each verse in the DSS pane, and in tooltips on the marked words (`/api/agreement`)
- Show differences: where reading panes show the same passage of two Hebrew corpora (e.g. MT/BHSA and SP), the words in which the texts differ are marked, compared on their consonants verse by verse. Vowels, accents and word division don't count; a difference in matres lectionis only is marked as spelling, any other as a variant; a plus is marked in the text that has it. Kept in the URL (`diff=1`)
- Clicking a word in the text opens the word in the node inspector, also where slots are signs (SP, DSS): signs within a word are no longer inspected one by one, and words shown as one unit in the pretty view are clickable
- Local display settings in `~/.cfabric/display/<org>/<repo>[@<version>].yaml`, layered over a corpus' app config
- Cite: a citation to copy for the passage being read or for a search (template and number of results), with the corpus' title, version and DOI and the software versions and date; `/api/health` reports the context-fabric version
- Query editor: completes feature values after `feature=` (also after `|`), most frequent first with their counts; hovering a feature shows its description, the object types it is on and its most frequent values; hovering an object type shows how many there are
- Saved workspaces: save the current panes, passages and templates under a name in this browser, open or delete them, and export or import them as files; importing a Text-Fabric browser job opens its query (and runs it) and its first passage
- A pane whose search the server no longer has (after a restart, or from an old link) searches again with its template
- Download dialog: choose extra feature columns per part of the results, besides those in the template, and TSV or TSV for Excel (`export.tsv?extra=3:lex,gloss`)
- Statistics on search results: how often each value of a feature occurs on one part of the results (by default a feature the template leaves open, such as `lex*`), and how the results spread over books or chapters; with a table view, and links to read each section
- Library list: copies of one corpus (same title, e.g. a fork) are listed once, keeping the newest data; each entry shows the version that opens; corpora can be hidden with `library: hide:` in `~/.cfabric/browser.yaml` or `--hide`
- Corpus library: open other corpora found on this computer while the browser runs (`--no-library` switches this off)
- Template problems as structured data (line, message, feature or node type), including problems inside quantifiers that the search engine only logs

### Fixed
- Standalone program on Windows: it didn't start when unpacked with Explorer from the downloaded zip, because .NET Framework refuses assemblies marked as downloaded (`Zone.Identifier`) and the window needs one (pythonnet's `Python.Runtime.dll`). The program now takes that mark off its own libraries at startup. Any failure of the window now falls back to a web browser.
- Switching between interfaces:
  - the Reader, the Interlinear and the Concordance passed on only their own corpus when no other texts were chosen;
  - a search in the reference corpus' pane no longer pushes out the only pane with the passage (*Panes*);
  - going through *Panes* no longer forgets the passage or the search of the interface before;
  - an empty Concordance doesn't open the search panel in *Parallel*.
- The Concordance on a phone: the facets fold away behind *Filters*, and the page scrolls as a whole.
- Switching from *Panes* to *Parallel* could leave an empty page when the panes showed exactly the open corpora, in their order: the two interfaces shared a cache entry for the corpus cards
